# Service hosting, storage and trustworthy receipt boundary

Status: proposed engineering, not provisioned or implemented. This specifies service lifecycle boundaries, not agent internals.

## Selected control-plane deployment shape
GoldGraft BFF/API runs as a Render web service, static browser bundle served same-origin; durable dispatcher is a separate Render background worker. Managed Render Postgres 18 stores case/authority/readiness/action/outbox/event metadata. Render host adapter reads the merchant service through a separate scoped host credential; it must never reuse service-administration authority from GoldGraft's own deployment account. Use separate service accounts/roles and configuration. GoldGraft's hosting and merchant's hosting are distinct even when both use Render.

Trusted acquisition and brokers run in separate service processes with per-component workload roles; no shop code executes in these services. Private raw/work/evidence blobs use AWS S3 with customer-managed KMS encryption, block-public-access, TLS and tenant/job prefixes; credential handles resolve via AWS Secrets Manager, not raw Postgres/ledger fields. Dedicated KMS permissions per broker; signer separate from source/model services. Raw blobs are never copied into metadata DB backups. Model inference and sandbox vendor accounts are GoldGraft-owned processing relationships disclosed to controllers, not merchant sign-in/password collection.

Named first deployment region target: Render Virginia and AWS us-east-1 for service storage/credentials; execution/model geography must be independently verified and named before disclosure. US storage does not imply US-only model processing. If the vendor cannot meet actual processing-location requirements, hold source transfer; do not promise residency from a storage setting. Vendor/account/plan/region/pricing checks remain prerequisites, no deployment performed.

Service workload identity: choose Render-managed OIDC to AWS STS roles with exact service/environment/workspace subject and audience, not wildcard workspace trust. Official documentation requires Pro workspace or higher; if unavailable, mark provisioning gate rather than using broad long-lived AWS keys silently. Raw merchant-host key remains a separate vaulted credential, never a provider password. Distinguish Render-issued workload token from end-user OAuth: OIDC here does not solve merchant Render consent.

Operational admission: fixed dependency lockfiles/container digests; private health checks, structured redacted logs, correlation IDs, per-principal rate limiting, immutable authority/receipt events and controlled clock synchronisation. Unknown spend cap, vendor quota, unavailable DB durable commit or missing processor terms prevents readiness/acceptance. Readiness checks prequalified template/capacity catalogues; it does not allocate merchant-source executable work before Start.

## Trusted first-operation collection
Use the E2B management channel from the trusted lifecycle adapter to invoke a fixed versioned baseline verifier before launching any shop-controlled executable or model task. The verifier reads acquired manifest and baseline files, computes exact accepted digest, and returns bounded typed result. Controller correlates provider execution/VM identity, assignment/generation, trusted command identity, transport result, source/scope/template digests and timing; stores raw bounded evidence then emits service-signed WorkerOperation only after validation. Keep evidence signing key outside VM. Do not give guest a general receipt-signing or provider management credential. An authenticated transport returning arbitrary stdout is still insufficient: validate verifier identity and result before any untrusted process can run. If vendor channel cannot establish this correlation/ordering, qualification fails.

Service signs immutable accepted/operation evidence with Ed25519 outside untrusted work, binding canonical payload digest, signer key ID and schema version in a separate authenticity envelope. Existing `authenticity_ref` points to this verified envelope. Signatures prove integrity/attribution only, not full payment correctness. Key rotation preserves verification history; no publication of private payloads to public transparency logs.

## Read/write scopes and deletion
Source broker holds only GitHub read authority; host broker holds only qualified Render workspace read authority. Storage writer scoped to one tenant/job; reviewer projection cannot acquire secrets or mint broker capabilities. Evidence and metadata may outlive code only within disclosed redacted retention. Delete active raw objects including incomplete uploads and noncurrent versions under an explicit sweep; verify actual inventory, not just a lifecycle policy. No automatic raw-object replication/backup. Metadata backups have a separately disclosed maximum 30-day expiry and restore-time tombstone/deletion replay before serving any restored case. This is a policy requiring future operational tests, not proof S3 lifecycle deletion is immediate.

Processor exports, support copies and vendor snapshots are distinct stores. Pending/unknown/held status must remain visible until each applicable deletion/expiry acknowledgement is known. No merchant payment credentials, active shop runtime or required callbacks are removed as generic GoldGraft cleanup.
