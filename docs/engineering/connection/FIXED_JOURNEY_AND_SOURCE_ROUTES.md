# Fixed journey; variable source and hosting connections

Latest user direction: keep the GoldGraft journey stable while source locations and hosting services vary. This is a Plan1 paper amendment only. It does not implement adapters, change accounts, import merchant code or advance Plans2–6. GitHub prevalence and claims that non-GitHub cases are rare have not been measured.

## Permanent product steps
Enter shop → Sign in → Obtain maintainer/controller permission → Connect code → Connect running shop/components → Automatic checks → Review scope and Start → Saved progress with verified operation evidence.

“Connect GitHub” remains the default named option inside Connect code, not a mandatory gate every merchant must pass. The user sees GitHub first and “Code is somewhere else” / “Ask maintainer”. A returning case resumes its selected source route without repeatedly presenting choices. Actual controller approval remains necessary for every location. Nontechnical owner is never forced to locate repos, map deployment files or invent credentials.

## Source routes in the same case
| Where code is | Product action and engineering treatment |
|---|---|
| GitHub | Connect GitHub through selected read-only Reader App; pin actual commit and source manifest. Existing first reference. |
| Another Git service | Choose source provider; adapter verifies identity/role, selected resource read-only scope, revision and bounded archive acquisition. GitLab/Bitbucket are candidate adapter families, not implemented or currently qualified support. No forced move to GitHub. |
| Local project folder or synced cloud folder | Actual maintainer selects the project folder in browser after disclosure and relation authorisation; resumable upload of approved files, no mandatory ZIP/terminal/install. Snapshot manifest substitutes for Git commit identity. Browser cannot silently browse the disk or synchronise a closed laptop. |
| Cloud drive/file storage | Prefer a qualified provider file/folder read route with sufficient narrow authority and revision/completeness checks. Where none meets genuine read-only/minimisation, actual controller can select an already locally synced folder or use provider-native download then choose those local files. Do not claim automatic direct Drive support until qualified. |
| Code only on host | Actual host controller contributes safe read-only export of the selected application through a qualified host adapter; exclude data/keys, preserve deployment/artifact linkage. SFTP/hosting-panel/cloud-object routes need their own narrow auth and extraction qualification. No broad server admin token or production shell execution to force connectivity. |
| Owner has no code/access or does not know | Ask maintainer in same case. Owner shares shop URL; contributor identifies actual source/host and approves requester/shop/resources/recipients. If no controller/source is obtainable, save Setup needed; a public website cannot disclose private backend source. |
| Platform owns checkout/code | Explain platform boundary and supported native migration/extension route where researched. Do not pretend downloaded HTML is backend/payment source or ask owner to upload code they cannot control. |

## Local-folder route: how to build it
1. Authenticate contributor, bind intended case/shop/recipient relationship and disclose that selected code will be copied to GoldGraft. For local files, selection proves device read access only, not exclusive ownership. Record controller declaration/provenance as attested; obtain responsible maintainer/controller approval and actual host controller's source/environment relationship approval before private disclosure to other recipients. Host control alone does not prove rights over arbitrary supplied files. Disputed rights remain a hold; no fake provider ownership claim.
2. On explicit user gesture, prefer showDirectoryPicker with mode read where supported; use directory file input fallback with relative paths. Never request filesystem write permission. Feature-detect/test browsers and accessibility. No unsupported claim that a tab can scan arbitrary laptop folders. Cancel leaves existing saved case intact.
3. In browser worker, enumerate only selected project root, apply deny rules for .git, credentials, .env, uploads, production datasets/order files and unrelated binaries; present a short file/count/size and exclusion summary. Handle browser-hidden files, empty/missing directories and unsupported linked files as explicit completeness checks. Do not serialise full absolute local paths. A compromised browser/client can bypass scanning, so trusted service repeats all validation/quarantine/exclusion before any work/model access.
4. Use authenticated tenant/case/binding-scoped upload session with per-file relative path/size/hash manifest, byte/count/quota limits, short-lived chunk capabilities and idempotent chunk identity. No public write/read bucket capability, path traversal or unbounded upload. Browser uploads only eligible files; failed exclusion policy prevents transmission of affected content. Network/credential log hygiene applies.
5. Server finalises only when expected file list/chunks and hashes agree. Create immutable snapshot digest, original versus excluded manifests and capture time. Preserve empty/expected-path semantics or hold on incomplete dependency set. No source_commit invented for local files. File modification during upload invalidates that file/capture; reselect/re-hash and produce a new immutable snapshot, never silently mix revisions.
6. Connection interruption resumes received chunks under the same authenticated upload session, bounded by custody TTL. Browser may need folder reselection and permission after closing/restarting; do not promise durable disk permission/background syncing. Only a fully acquired server snapshot supports later laptop-independent managed work. TTL/cancel deletes incomplete chunks separately with evidence.
7. Apply the same host/artifact/correspondence gates as Git. Uploaded folder may be stale, incomplete, local-only or uncommitted. Its digest alone never proves deployed correspondence. Match file/build manifests to actual authorised host artifacts and current runtime; if unavailable, code is received but Match not verified/Start held.

## Cloud drive permission investigation and safe outcome
Google's scope catalogue distinguishes broad read-only Drive content access from selected-file drive.file, which permits writes. Requesting both is not a read-only intersection. Therefore reject drive.file as a “genuinely read-only” service grant, and do not silently replace it with whole-Drive access. A direct adapter must establish provider-enforced narrow read authority (or a genuinely read-only account/resource role whose effective scope meets the stated boundary), exact file grants, revision consistency, recursive completeness, shortcut/shared-drive boundaries, download permission and revocation. No such Google Drive adapter is qualified here. Provider-native download/local selection is the honest fallback, with its extra effort disclosed; no forced migration or ZIP creation. Similar evidence gates apply to OneDrive/Dropbox/object-storage routes rather than assuming identical permission semantics.

## Generic proposed source contract
SourceSnapshot/1 = {source_kind: git|local_folder|cloud_files|host_export, source_provider: registered_provider_id, source_resource_id: str|null, revision: {kind: git_commit|provider_revision_set|capture, value: str}, manifest_digest: sha256, file_count: nonnegative_int, total_bytes: nonnegative_int, captured_at: UTC timestamp, omission_manifest_ref: str, authority_binding_refs: str[], provenance_class: provider_reported|controller_attested|verified_build_link, completeness: complete_for_declared_scope|incomplete|unknown}.

These are proposed new fields/formats only. Common readiness, accepted scope and operation evidence bind snapshot+resource-graph digests; git_commit is present only for Git routes. Start/queue/cancellation protocol is unchanged. A capture identifier is not a Git revision or proof of host identity.

## Proposed targets and meaningful validation
contracts/.../connector_adapters.py extends source types; pieces/connector/providers/local_upload.py and upload_sessions.py implement bounded local transfer; pieces/web/src/connection/SourceChoice.tsx and LocalFolderInput.tsx handle stable route choice/feature fallback; a separately qualified cloud_files.py/host_export.py implements provider-specific mechanisms, never an arbitrary URL reader. All are future paths, no product files changed.

Acceptance must cover secret/customer-data canaries before upload and at quarantine, browser permission/cancel/expiry/reselection, interrupted/double chunks, edits mid-capture, malicious client traversal, storage expiry, incomplete cloud folder grants, write-capable scope rejection, wrong/stale source-to-host match and owner without controller. Claims of “most” require observed target-user source/host inventories and denominator; maintain a route capability register rather than inventing a percentage.

Primary evidence: [browser read-only folder picker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker), [directory-input fallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/webkitdirectory), [Google Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [Drive download/revision capability](https://developers.google.com/workspace/drive/api/guides/manage-downloads). These support mechanism/limitations, not a built GoldGraft route or empirical user prevalence.
