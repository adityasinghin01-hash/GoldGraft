Follow the [three-channel team workflow](TEAM_CHANNELS_AND_SPONSOR_ACTIONS.md) and [source-inspected reply to Vijay](VIJAY_TEAM_INPUTS_REPLY.md).

## 1. Render

Gupta owns the existing control-plane web service, worker/Postgres and first-reference host mechanism. GoldGraft's service-host credentials must remain separate from merchant-host grants even when both accounts use Render. Singh coordinates service operation; Vijay supplies the qualified reference shop/domain recipe.

Acceptance: a versioned service/worker/database configuration, restart/durable-acceptance observations and an exact-image/config deployment trace for the separately approved reference path. A free or credited service cannot replace required OIDC, storage, durability or authority capabilities. Do not force a merchant host migration to create sponsor use. Render Workflows is not an additional scheduler.

Sources: [selected service design](../connection/SERVICE_AND_STORAGE_SPEC.md), [Render resource](https://paypalaihackathon.devpost.com/details/render).

## 2. Kernel

Vijay owns browser scenarios for the reference shop: checkout, payment popup, buyer approval/return, cancellation and permitted fault paths. Gupta supplies guarded browser/runner integration, scoped session access and recorder correlation. A replay explains what happened visually; it does not itself prove money correctness.

Acceptance: actual authorised browser operations and replay, associated case/run/scenario/subject identities, independent recorder evidence, and explicit missing/unknown outcomes. Restrict target URLs, credentials, replay access and retention. E2B remains the source-execution isolation target. Review the vendor's [4 November security notice](https://www.kernel.sh/blog/public-notice-of-security-incident-nov-4-2026) before any credential/private-session use; missing qualification holds this adapter.

Source: [Kernel resource](https://paypalaihackathon.devpost.com/details/kernel).

## 3. AG Grid and AG Studio

Singh owns the UI contract; Antigravity implements under pieces/web. Singhal supplies recipient-safe review/evidence projections. The concrete review question is: which scenario failed, what evidence is missing, and which exact artifact produced that result? Grid filtering and linked basic charts support this investigation.

Acceptance: sortable/filterable scenario rows, evidence drill-through, matching summary denominators and visible unknown/missing states. Private details are removed server-side, not merely hidden in columns. Optional Studio work must add genuine linked widgets/layout interaction; an optional Studio agent may query only approved aggregates and manipulate dashboard presentation, never payment, source, secret or deployment authority. Community views do not automatically establish Studio use or award eligibility.

Sources: [frontend owner guide](../../START_Aditya_frontend_agents.md), [AG sponsor brief](https://paypalaihackathon.devpost.com/details/aggrid).

## 4. Bryntum

Singh/Antigravity display the temporal/dependency explanation of the same authoritative run, using Gupta's committed state/events and Singhal's safe projection. This is different from AG's evidence table: it answers what is waiting on what, when a retry happened, and why delivery or exit is pending.

Acceptance: dependency edges, known observed intervals, milestones and a selected blocker linked to its source event. Duplicate/out-of-order events cannot fabricate progress. Disable task creation/dragging/rescheduling mutations. Do not describe a displayed dependency as a vendor scheduling decision, or an observed wait as premium critical-path analysis. Select only features supported by the actual package/licence; do not add a second scheduler.

Sources: [Bryntum resource](https://paypalaihackathon.devpost.com/details/bryntum), [Gantt feature boundaries](https://bryntum.com/products/gantt/features/).

## 5. APIMatic

Vijay owns payment-domain SDK recipes and fixtures. Singh uses the same grounded context for Architect/Grafter code authoring; Gupta consumes qualified adapters without sharing another piece's implementation. The purpose is avoiding fabricated endpoint names, SDK symbols and request shapes.

Acceptance: a pinned plugin/document/SDK version, operation-to-real-symbol mapping, compiling adapter example and positive/negative request fixtures. SDK-generated types stay behind adapters; canonical Python contracts and the shared change process retain wire authority. Plugin installation alone is not substantive usage. This development aid must not become an expiring runtime dependency of merchant payments.

Source: [APIMatic resource](https://paypalaihackathon.devpost.com/details/apimatic).

## 6. Postman

Gupta owns collections covering case access, controller/grant revocation, readiness, durable Start/cancel, stale generations, exact approval/effect slots, unknown results and exit. Vijay adds approved sandbox/domain scenarios; Singhal adds tamper, missing-proof and private/public projection negatives.

Acceptance: repository-reviewable collections, empty-secret environment templates, versioned expected responses and actual results for the authorised check class. No arbitrary cross-piece imports or duplicate wire definitions. Ordinary automated tests remain offline; external collection runs require their separate scope. Manual/API examples, mocked results and actual sandbox/provider evidence are labelled separately. Team collaboration features and data-driven runner features are not assumed available.

Sources: [PayPal collections](https://www.postman.com/paypal), [Postman resource](https://paypalaihackathon.devpost.com/details/postman).

## 7. Elastic

Singhal owns evidence-search usefulness and exact-subject retrieval requirements; Gupta supplies redacted diagnostic ingestion and server-enforced recipient/case access. Search by run, task, scenario, artifact subject, reason code and missing-evidence category should take a reviewer to the canonical artifact. Optional public-document retrieval can support grounded API lookup.

Acceptance: a versioned redacted index mapping, representative queries, correct source-artifact drill-through, stale-index handling and cross-case/revocation negatives. Search summaries must preserve unknowns. The authoritative ledger/store and deterministic proof are unchanged; ranking or an LLM answer cannot issue a proof verdict. No raw customer/payment bodies, secrets or unapproved private-source indexing.

Source: [Elastic resource](https://paypalaihackathon.devpost.com/details/elastic).

## 8. Zapier

Gupta owns an opt-in connector consuming committed minimal events; Singh supplies concise truthful notification copy and authorised case links. Useful notices include controller action needed, a blocked prerequisite, a result available or exit still pending. The merchant must not keep polling the browser solely to discover an unavoidable action.

Acceptance: one permitted minimal notification per logical event, retry/deduplication evidence, opt-out and delivery-failure/quota-exhaustion handling. Notifications are not approval receipts; recipients act through the authenticated case/controller surface. No automatic invitations, payment/capture/refund/deploy operations, secrets, sensitive payloads or sole safety-alert dependency. Losing this connector must not change task, proof, approval or exit state. No messages are sent by this documentation update.

Source: [Zapier resource](https://paypalaihackathon.devpost.com/details/zapier).

## 9. Astropods — conditional

Gupta owns any future GU02 gateway adapter and credential/processing boundary; Singh owns the SI04 task/prompt/model evaluation. A meaningful use would demonstrate a concrete capability, model-access or operating-cost advantage under the same permitted synthetic task/tool constraints as the existing direct-Claude route.

Acceptance: exact model/profile identity, processor/retention/region/cost qualification, correctly handled tool calls and usage receipts, enforced budget, cancellation and unknown-response reconciliation. Mere routing of the same call through an extra vendor is insufficient. No second orchestration/state authority, E2B replacement or automatic model/provider fallback. Direct Claude and its existing budget remain the current choice unless Aditya explicitly changes them. If no advantage is evidenced, record not justified instead of forcing adoption.

Sources: [Astropods gateway](https://docs.astropods.com/ai-gateway), [gateway limitations](https://docs.astropods.com/ai-gateway/limits).

## 10. Channel3 — conditional

Vijay owns an optional reference-catalog preparation and domain-regression task, not a new shopping/discovery feature or merchant catalog replacement. A justified use would expose a currently uncovered product/offer/variant substitution or checkout-line-item mapping defect using rights-cleared real-world records.

Acceptance: demonstrate the existing fixture gap first; obtain specific storage/sharing/redistribution rights; then record a bounded dataset's provenance, allowed fields, transformations and digest. Exactly the same approved snapshot feeds OLD/OLD_TWIN/NEW. Compare product/variant/offer identity, quantity, integer minor-unit amount/currency and the supported shop/provider line-item semantics. Missing attributes stay missing; Channel3 does not establish tax rules or money truth.

Ordinary tests remain offline, with no catalog refresh or remote images. Public caching advice does not establish a durable, redistributable test-data licence. No retailer image/data is copied merely because API access exists. If rights or actual incremental test value cannot be established, retain existing licensed fixtures and record Channel3 not justified. Preparation-time use is not automatically a meaningful product-experience integration for its sponsor award.

Sources: [Channel3 resource](https://paypalaihackathon.devpost.com/details/channel3), [publisher terms](https://trychannel3.com/terms/publishers), [caching guidance](https://channel3.ai/docs/guides/caching).

## Ownership and evidence rules

1. Each primary owner records actual use or a precise held/not-justified disposition with the package, version, purpose, data scope, permitted access, cost/expiry, licence and reviewable artifact. Teammates can reuse an artifact without inflating the sponsor count.
2. Separate development aid, actual product integration, vendor/provider qualification and prize eligibility. None implies another. Account signup, reading documentation and a mock success alone do not count as working integration.
3. New shared record/route needs still go through SI01 and the existing format-change process. No field names in this planning document invent current wire support.
4. No sponsor service receives another owner's authority: GU owns control/effects/custody, VJ domain recipes, SH proof and Singh policy/UI coordination. Antigravity retains frontend implementation ownership.
5. External capability/licence/security qualification remains necessary before use; this document authorises no account action, credential intake, private-source transfer, model/payment call, deployment, publication or teammate message. Plan6 is separate.
6. The current assignment is to maximise meaningful coverage across the whole team, not to place every service in the merchant's critical path or manufacture a feature solely for a sponsor. Review conditional cases before adding dependencies.

The official [rules](https://paypalaihackathon.devpost.com/rules) list the ten partner tools as optional, require authorised third-party use and meaningful functioning software, and limit a project to one sponsor prize. More names do not establish stronger implementation or an award.
