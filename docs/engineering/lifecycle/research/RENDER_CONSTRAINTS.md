# Plan3: Render safe-delivery constraints

Public-document research checked **6 November 2026**. Paper constraints and proposed acceptance cases only; no account access, authenticated API requests, deployments, jobs, or secret inspection. Inputs inspected: Plan1 `HOST_ADAPTER_FEASIBILITY.md` and `CORRESPONDENCE_SPEC.md`. Their digest-pinned reference remains conditional, not qualified by this research. **Documented** below means the public contract; **required/proposed** means an engineering acceptance requirement, not a provider guarantee.

## 1. Artifact identity: image-backed and Git-backed differ

- **Documented:** Docker supports either pulling a prebuilt registry image or building a Dockerfile from Git. A Git-backed Docker service is still Git-backed; using Docker does not establish deployment of an independently approved image. Git builds can also receive service environment variables as build arguments. Required: pin build inputs and exclude secrets from image layers. [Docker on Render](https://render.com/docs/docker)
- **Documented:** image-backed services accept digest references, require `linux/amd64`, and do not automatically redeploy when a tag changes. Render pulls registry images again for deploys and may need another pull for restart or scale-out. Required: retain the approved digest and usable pull authorization for operation and recovery. An immutable digest does not guarantee registry availability. A deploy-hook image override changes that deploy, while subsequent deploys use the configured reference; hooks can mutate through GET and must never be treated as harmless links. [Prebuilt images](https://render.com/docs/deploying-an-image)
- **Required:** bind source revision/manifest, approved build instructions, provenance subject digest, selected Render service/environment, actual deploy identity, and effective configuration. `commit.id` alone proves neither reproducible build output nor running bytes. A tag, source push, successful CI check, or GitHub deployment badge cannot substitute for that chain.
- **Documented:** GitHub attestations link an artifact to source/build information; verification and an explicit trust policy are necessary, and an attestation is not a security guarantee. Required: reject a valid signature from an unapproved workflow/repository or for the wrong digest; do not presume every dependency/config field is included. [Attestation semantics](https://docs.github.com/en/actions/concepts/security/artifact-attestations)
- GitHub's container-attestation example uses `subject-name` and `subject-digest`. Its documented generation permissions include `contents: read`, `id-token: write`, `attestations: write`, and `packages: write`. These are build/publication capabilities, not Render deployment permission. Private/internal repository attestations currently require Enterprise Cloud; do not solve an entitlement gap by publishing private source. [Generation and availability](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)

## 2. Verified public API contract: exact deploy and polling

Base URL: `https://api.render.com/v1`. Inspected the public [OpenAPI JSON](https://api-docs.render.com/openapi/render-public-api-1.json) in memory: `info.version=1.0.0`; downloaded-byte SHA-256 `e9127b4b3b718d170607ece5b9cee72350deed1aa0f3d024421319f7ab83eb95`. This identifies the inspected schema, not a stable provider release or evidence of account entitlement.

| Public operation | Verified contract and required interpretation |
|---|---|
| `POST /services/{serviceId}/deploys` | For an image-backed service, body `{"imageUrl":"<registry>/<namespace>/<image>@sha256:<digest>"}` requests a pinned image. Host, repository and image name must match the service's configured image. `imageUrl` cannot combine with `buildId`, `commitId`, or `deployMode: deploy_only`. |
| Same endpoint, Git-backed | `commitId` selects a commit; omission defaults to the connected branch's latest commit. API selection of a commit **does not disable auto-deploys**. `buildId` selects a Build Source build and cannot combine with `commitId`, `imageUrl`, or `deployMode`; this is a separate path needing qualification. |
| Deploy response | `201` documents a `deploy` object; `202` means queued but has **no response-body schema**. Only `id` is required in the deploy schema. Never assume a queued response includes a deploy ID. |
| `GET /services/{serviceId}/deploys/{deployId}` | Retrieve and poll the exact accepted deploy ID. Documented optional fields include `status`, `image.ref`, `image.sha`, `commit.id`, `trigger`, and timestamps. `image.sha` is the SHA resolved when the deploy was created; `image` is absent for Git-backed deploys. |
| `GET /services/{serviceId}/deploys` | Supports `status`, time filters, `cursor`, `limit`; response is an array of `{deploy, cursor}` entries. Use bounded pagination for reconciliation; neither “newest” nor `finishedAt` alone establishes the current live version. |
| `POST /services/{serviceId}/rollback` | Required body `{"deployId":"<previous-successful-deploy-id>"}`; `201` returns a deploy object. Poll the **new** rollback deploy ID. API rollback leaves auto-deploy enabled. |
| `POST /services/{serviceId}/restart` | `200` is documented as “Service restarted”, without a deploy-object response contract. Do not invent a returned deploy ID. Restart permission must be qualified separately. |
| `GET /services/{serviceId}/instances` | Array of `serviceInstance` objects with only required `id` and `createdAt`. No documented per-instance health, deploy ID, image digest, or config version. |

Contracts above are from the [OpenAPI](https://api-docs.render.com/openapi/render-public-api-1.json), cross-checked against [Trigger deploy](https://api-docs.render.com/reference/create-deploy) and [List instances](https://api-docs.render.com/reference/list-instances).

Exact status enum: `created`, `queued`, `build_in_progress`, `pre_deploy_in_progress`, `update_in_progress`, `live`, `deactivated`, `build_failed`, `pre_deploy_failed`, `update_failed`, `canceled`. Proposed handling: pending states remain pending; failure/cancellation/deactivation cannot accept the candidate; unknown or missing states hold. `live` is necessary but insufficient: re-read selected-service live identity, resolved digest and effective-config evidence after bounded application checks. The schema does not specify SHA normalization or OCI index-versus-platform-manifest semantics; qualify equality against a single-platform reference rather than guessing. [OpenAPI](https://api-docs.render.com/openapi/render-public-api-1.json)

**Unresolved acceptance blockers:** the inspected trigger operation documents no idempotency key or request-correlation field, and a `202` or lost response can leave acceptance ambiguous. Proposed: bounded reconciliation; if the exact request cannot be identified uniquely, hold without replaying the mutation. Back off on rate limits/read failures; never turn a polling failure into another deploy. No universal retry/deadline values were established.

## 3. Instance health, restart and disk recovery

- Render probes each web/private service instance. Defaults are TCP checks; custom HTTP checks are web-service-only and accept `2xx` **or `3xx` within five seconds**. New deployments require all new instances to pass simultaneously within 15 minutes. Running-instance failures remove traffic after 15 seconds and cause restart after 60 seconds. Required: an operation-relevant, side-effect-free readiness check; a redirect to login or open port is insufficient application evidence. **Blocker:** instance listing cannot independently establish Plan1's all-instance version/health requirement; one load-balanced HTTP success cannot establish it either. A separately qualified evidence method is required. [Health checks](https://render.com/docs/health-checks), [instance schema](https://api-docs.render.com/openapi/render-public-api-1.json)
- Restart creates replacement instances using the running Git commit/configuration; saved but undeployed environment changes are not incorporated. Overlapping deploy policy can wait for the newest request while skipping intermediate requests, or override an in-progress deploy. Cancellation can start an already-waiting deploy. Required: reconcile competing deploys before declaring either delivery or recovery complete. [Deploy lifecycle](https://render.com/docs/deploys)
- Persistent disks preserve only their mount subtree; other writes disappear on redeploy/restart. A disk permits one instance, is unavailable during build/pre-deploy/one-off jobs, and prevents zero-downtime deploys: the old instance stops first. Required: an explicit outage allowance and a viable runtime migration/recovery procedure for flat-file state. Never promise that a pre-deploy task migrates an attached disk. [Persistent disks](https://render.com/docs/disks)
- Code rollback does **not** roll back disk data. Snapshot restore replaces the disk and loses changes after the snapshot; it is not partial recovery. Render warns against snapshot-based recovery of custom databases. Required: define compatible state/schema transitions, backups, and reconciliation before accepting recovery of orders/payment records. [Disk recovery](https://render.com/docs/disks)
- Rollback reuses some target settings, including service environment variables, but does not restore environment-group values; a deleted group can be omitted. Disks, domains, compute plan and underlying platform changes are not reverted. Tagged images can resolve to different bytes, and unavailable registry images fail recovery. Current service settings remain for subsequent standard deploys. Required: verify recovery artifact, configuration and state independently; “rollback successful” cannot mean “everything restored”. [Rollback semantics](https://render.com/docs/rollbacks)

## 4. Configuration provenance and permission boundary

- Render can save environment values without deploying, deploy an existing build with new values, or rebuild/deploy. Direct service variables override group variables; precedence between colliding groups is not guaranteed. Linking a group deploys the service; changing a group can redeploy linked services with auto-deploy enabled. Required: distinguish stored, build-time and active runtime configuration, record nonsecret configuration identity plus secret names/references/version evidence, and reject ambiguous group collisions. [Environment configuration](https://render.com/docs/configure-environment-variables)
- **Blocker:** `GET /services/{serviceId}/env-vars` returns value-bearing `{envVar:{key,value},cursor}` records; it is not a names-only provenance endpoint. The inspected deploy/instance contracts expose no effective-config digest or secret-version attestation. Required: preserve Plan1's denial of secret reads and hold if effective config cannot be proved through an independently qualified, secret-free record. Do not invent a Render `configVersion` field or hash secret values into the paper evidence. [OpenAPI](https://api-docs.render.com/openapi/render-public-api-1.json)
- Scoped keys remain early access, workspace-scoped and subject to breaking changes. Services configuration Read and secret-value Read are distinct permissions. Deploys Read views history/status; Deploys **Run** also permits triggering, cancellation and rollback. Services write separately covers configuration and preview/one-off management. Required: retain Plan1's read-only grant for inspection; any later delivery authority must be separately authorized and qualified. Run is not a narrow “deploy one approved digest” grant. [Scoped permissions](https://render.com/docs/scoped-api-keys)
- **Blocker:** the inspected public schema specifies HTTP bearer authentication but no scope-introspection operation; the permission table does not explicitly map restart or every endpoint. Successful reads, key naming, endpoint tags and a documented Run category do not prove effective least privilege. Account entitlement, exact endpoint coverage and denial evidence remain future qualification gates, with no classic-key substitution. [Scoped permissions](https://render.com/docs/scoped-api-keys), [OpenAPI](https://api-docs.render.com/openapi/render-public-api-1.json)

## 5. Source publication can itself cause delivery

- Connected Git services normally auto-deploy on branch pushes/merges. Render's “After CI Checks Pass” accepts `success`, `neutral` and `skipped`; it is not evidence every intended test executed. Required: separate publication approval from deployment authority and inspect effective triggers before any future push. API commit selection/rollback cannot be relied on to turn those triggers off. [Deploy behavior](https://render.com/docs/deploys), [API rollback](https://render.com/docs/rollbacks)
- Blueprint changes can redeploy affected services independently of the intended source-delivery path. Required: include Blueprint auto-sync and configuration effects in publication review; disabling an application service's auto-deploy must not be presumed to disable Blueprint sync. [Blueprints](https://render.com/docs/infrastructure-as-code)
- PR creation, title/label changes and pushes can provision/update previews. Service previews initially copy base settings, including database connection variables. Required: establish test-only credentials/data/destinations **before creation or execution**, rather than fixing copied production connections afterward. A preview URL is not proof of isolation. [Service previews](https://render.com/docs/service-previews)
- Full preview environments create resources and can run initialization hooks; copied datastore/disk resources contain no base data. `previewValue` can override variables, while `sync: false` placeholders are not copied. Required: explicitly qualify environment groups, external targets, seed behavior and cleanup; copied infrastructure does not establish safe payment isolation. [Preview environments](https://render.com/docs/preview-environments)
- GitHub `push`, PR, `pull_request_target`, `workflow_run`, deployment and dispatch triggers need review. Do not execute proposed-source code in a privileged `pull_request_target` job. [Workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- Current GitHub docs say `GITHUB_TOKEN` generally suppresses recursive runs, but dispatch events run and certain automated PR events produce approval-required runs; App/PAT events can trigger normal workflows. This is not a Render trigger control. Required: never use token choice as proof that publication has no execution side effects. [Trigger rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
- GitHub environment protections apply to jobs referencing that environment; reviewers, bypass settings and private-repo availability must be checked. A misspelled/new environment can be created without protections. Required: do not assume these gates govern Render's independent Git integration or credentials available through another path. [Environment gates](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
- GitHub deployment objects/statuses dispatch events consumed by integrations; creating a “delivery receipt” can therefore trigger work. They are not independent runtime attestation. Required: source publication permissions, build/package publication, GitHub deployment writes and Render Run remain separately approved capabilities, with their indirect triggers included. [GitHub deployment semantics](https://docs.github.com/en/rest/deployments/deployments)

## 6. Proposed failure acceptance cases — not executed

These are paper cases for later authorized fixtures/disposable references. Passing means the specified failure is handled safely, not that production is qualified.

| ID | Injected failure | Required acceptance outcome |
|---|---|---|
| R01 | Git SHA matches, but rebuilt dependency/base image differs; or Docker Git service is misclassified as image-backed | Exact-artifact claim blocked; no inferred digest correspondence. |
| R02 | Mutable tag moves, image digest is missing/wrong, or multi-platform digest equality is unexplained | Delivery/recovery verification holds; never silently substitute latest/tag bytes. |
| R03 | Provenance is correctly signed for a different source, subject, builder or workflow revision | Reject correspondence despite valid signature. |
| R04 | Trigger returns `202` without ID, response is lost, or several same-image deploys appear | State remains ambiguous pending unique reconciliation; no blind POST retry or guessed deploy ID. |
| R05 | Poll yields pending, unknown/missing status, `429`, transient failure, cancellation or deactivation | Bounded reads/backoff; explicit pending/held/failed outcome, never success from HTTP acceptance. |
| R06 | Candidate goes live, then another deploy supersedes it; cancel releases a queued deploy | Reconcile actual live identity and fail candidate acceptance on drift. |
| R07 | One endpoint succeeds while another instance is unhealthy/old; HTTP readiness redirects to login | No all-instance/application-readiness claim from instance IDs, TCP or a single response. |
| R08 | Disk-backed swap fails startup after old instance stops | Recognize outage; invoke only separately authorized recovery; no zero-downtime guarantee. |
| R09 | Flat files are written outside the disk mount, or migration assumes pre-deploy disk access | Reject persistence/migration readiness before delivery. |
| R10 | New schema/state is incompatible with old image; snapshot predates accepted transactions | Code rollback alone is insufficient; block destructive restore pending explicit loss/reconciliation decision. |
| R11 | Prior digest disappears or pull credentials expire before rollback/restart/scale-out | Recovery feasibility fails; no unavailable-artifact guarantee or tag fallback. |
| R12 | Saved config differs from active config; group collision/deletion/rotation changes recovery semantics | Config correspondence holds; no secret read or claimed config-version API to close the gap. |
| R13 | Only Deploys Read exists; scoped access is unavailable/revoked or Run scope is unverified | Mutation unavailable; no grant widening or classic-key fallback. |
| R14 | Source push/PR/title edit would trigger Actions, Render deploy, Blueprint sync or preview | Publication-only handoff holds until side effects are separately authorized/contained. |
| R15 | Preview inherits production DB/payment variables or initialization contacts a live destination | Reject execution before provisioning/running; require test-only destinations and credentials. |
| R16 | Required CI check is skipped/neutral, or a privileged PR/downstream job consumes untrusted code | No test-complete/delivery approval inferred; privileged execution blocked. |
| R17 | Environment gate is unavailable, bypassable, misspelled, or irrelevant to Render's direct integration | No assumed approval boundary; delivery remains blocked until effective controls are qualified. |
| R18 | GitHub “success” deployment/status receipt is stale, wrong-ref, or triggers an integration | Never accept it as Render/runtime proof; treat receipt creation as a separate external action. |

**Key blockers carried forward:** per-instance version/health evidence; secret-free effective-config provenance; scoped-key entitlement/assurance and endpoint permission mapping; ambiguous queued-request reconciliation; state-compatible disk recovery and retained images; demonstrated separation of publication/preview effects from deployment authority. All remain unproven by public docs alone.
