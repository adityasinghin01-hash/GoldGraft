# Atomic delivery protocols — normative Plan4 corrections

Paper design only. These protocols supersede ambiguous earlier Plan3 state-transfer/approval/callback/exit wording. No implementation or account/financial/runtime test performed. Where a required primitive does not exist, admit a bounded supported profile or hold before mutation; do not invent a provider API or require hidden merchant technical finishing.

## IR01: bootstrap BEFORE the first destructive restart, then cutover
The first prerequisite storage/callback/maintenance installation is itself a consequential migration, not a harmless setup task. Render disk attachment can restart/deploy before any new mount contains prior ephemeral files. Therefore do not attach/provision via target redeploy until current state is already preserved and the transfer protocol is qualified.

1. Inventory every current state writer and handler: checkout creation, return/capture, refund/admin, queued task, notification/IPN/webhook, scheduled operation and multiple instances. Include economic intent/idempotency/origin ledger, not just paid orders. Record current provider/runtime/config/schema and exact original routes/credentials (references, no secrets in evidence). Obtain current resource approvals and target reservations below.
2. Establish a qualified merchant-controlled durable callback receipt path and origin-handler/intent-state route BEFORE diverting any event or stopping the target. Provisioning/registration/DNS/config changes require exact approved action slots, backup of current settings and reversible/current-compatible preconditions. A queue alone cannot serve a browser capture/return; that handler must stay live through a qualified merchant-owned bridge or sessions must fully drain under an explicitly approved bounded interruption policy. If neither can be provided, hold the migration while original keeps running.
3. Stop new checkout admission via an existing qualified authenticated merchant safety control. This is NOT a writer fence on existing sessions. Drain all existing browser captures/returns/refunds and tasks while durable notifications are queued/forwarded under origin identity. If a long-lived/unknown payment/session cannot be drained or safely served by the independent origin route, no cutover. The old store remains authoritative until the explicit fence below.
4. Establish a durable event high-water mark H and idempotent effect ledger. Before H, all accepted event effects are committed/acknowledged in the consistent export boundary; after H, events/requests are durably recorded but not applied by the old writer. Fence EVERY old writer/forwarder with target generation/epoch; wait for in-flight local writes/transactions to complete or reconcile them. External money can still settle; origin IDs and durable post-H input/reconciliation remain available. Do not assume “new checkout blocked” achieved this.
5. Export consistent current state using a pre-existing qualified read/export primitive while original data still exists, verify export digest/schema/counts/origin/idempotency consistency and store in encrypted merchant-owned recovery destination. Verify restore into disposable copy and replay mechanics before target restart. No unauthenticated orders endpoint or production customer dump into GoldGraft model. If existing ephemeral runtime offers no safe consistent export/fence/handler route, DO NOT redeploy to install an exporter: hold full delivery or use an explicitly approved independently qualified recovery route. The current bare fixture therefore does not yet qualify a live existing-shop migration.
6. Only after verified export and fence, perform approved first storage attach/prerequisite deployment or later code replacement. A sibling service cannot mount the same single Render disk. Restore/migrate under the single designated new writer, with no concurrent old writer. Verify schema/source/config and origin/idempotency ledger, then replay durable post-H events exactly once at the business-effect level using recorded identities; reconcile unknown external effects before additional financial requests.
7. Verify restored state plus backlog, required browser-return/capture routes, notifications and known pending/refund obligations. Old writer remains fenced; independent ingress keeps receiving. Reopen admission only when current target/state evidence meets scope. Failure after money/state changes uses compatible forward repair/qualified current-state cutback; never restore an old snapshot over newer economic records. Record H, export/restore/replay digests/counts/offsets and actual gaps.

Every preparatory mutation follows the same action/authority/reservation/effect rules. If an all-drained policy is chosen, it must include every required long-tail callback/handler obligation and an approved interruption allowance; reaching a timeout produces hold, never silently dropping outstanding work. Bootstrap/restore authority and real consistency/continuity tests remain open gates, not solved by this protocol text.

## IR02: resource-level reservations, not only per-run fencing
Before ANY live/shared publication, registry, route, data, deployment, recovery or cleanup mutation, acquire a durable reservation for canonical provider/account/environment/resource identities and all shared dependencies in the affected graph (repository/default target, registry destination, service, datastore/state namespace, callback routes). Tenant/case IDs do not partition the same physical target. Sandbox builds can run concurrently under separate quotas; live/shared effect groups require exclusion.

Acquire required keys in a stable canonical sorted order in one transaction, or atomically reject/retry without partial ownership. Persist owner case/run/action plan, lease, monotonic resource fencing epoch, expected resource version and unresolved effect references. Recheck current epochs before each effect; keep run generation as a separate worker fence. Another case/run targeting any reserved resource receives a clear conflict/queued hold, not parallel apply.

Lease expiry/crash fences the old executor but does NOT release target ownership while an external effect, writer or cleanup is unknown. Reconciler takes control of the same reservation under current authority/new resource epoch; only after all dispatched effects/current state are known may it transfer/release. Recovery itself obtains/retains the affected reservation; no new run cleans underneath it. Human/external provider actors remain outside GoldGraft locks: detect version/config/runtime drift and hold/reapprove; do not promise provider-wide exclusion.

Asset/grant inventory includes ownership=merchant|shared_service|exclusive_run, other active references, provider scope and cleanup authority. Remove only exclusive-run resources or case-specific access. Do not uninstall a shared App, revoke a shared scoped key/installation, delete a callback or artifact used by another run just because this case ends. Shared revocation requires explicitly approved wider-impact plan/current controllers and must first fence/reconcile affected uses. Required shared merchant assets remain preserved.

## IR03: exact image build, test, export and publish boundary
Candidate bytes alone do not create a deployable artifact. Trusted service issues ArtifactBuildRequest binding source/snapshot/tree, recipe/build context, single-platform linux/amd64 base/dependency digests, safe build-config/secret-reference policy, runtime limits and expected outputs. Gupta owns builder/runtime/recorder, Vijay recipe/domain fixtures; untrusted Dockerfile/build steps run in isolated builder without registry push, provider/live secrets or host Docker socket. No build/push on merchant laptop is required.

Build result exports immutable OCI image manifest/layers plus source/build/dependency/provenance manifest under bounded trusted collector. Record OCI manifest digest distinct from export-tar digest; do not compare different digest types or multi-platform indexes silently. Trusted signer outside guest attests observed inputs/artifact identity, not arbitrary guest claims. Scan image layers/export/config for secret/data leakage. Local source snapshot is not a fake Git SHA.

Run required baseline/candidate tests AGAINST the exact deployable image bytes (or qualified deterministic unpacked equivalent with exact digest match), not only a source tree. Review bundle/approval binds that artifact plus runtime/config/state evidence. A post-merge rebuild with changed bytes invalidates corresponding tests/approval. If merge changes commit metadata but approved source-tree/build inputs and exact tested image remain identical, policy must explicitly permit/verify that derivation; otherwise re-prove/reapprove.

Registry publication is separate from Git writes and Render Deploy Run. Obtain later controller-approved private destination write capability, recipient/privacy/retention and merchant ownership/pull rights; validate host/configured registry/name matches approved image target. A target registry/name/config change is a separately approved effect with trigger/state/recovery preconditions. Trusted publisher, not build guest, uploads exact validated manifest/layers, reconciles interrupted/duplicate uploads and verifies remotely addressable digest. Inspect registry hooks before first upload; direct-artifact and Git routes both use this boundary. Source bundle destination is private merchant-owned and authenticated; no public image/source to bypass entitlement. Missing registry/provenance/pull capability holds delivery, not manual merchant build/push homework.

## IR04: receipt, validation and business effects are distinct
For IPN: bounded ingress accepts original bytes/listener/environment and durable encrypted UNVERIFIED receipt, then acknowledges receipt (empty200 as appropriate), then retryable postback validation to pinned correct PayPal endpoint with original encoding/fields and business checks. No money/order effect until validation plus merchant/order/status/amount/currency/origin checks. Verification timeout remains unverified with recoverable receipt; INVALID has no business effect. If durable receipt unavailable, do not acknowledge as accepted; explicit non-success/connection outcome permits provider retry but finite delivery still needs reconciliation. Apply size/rate/quota/private-retention controls to unauthenticated input; no raw data in model/public reports.

REST webhook follows its own correct listener/app/raw-body/transmission validation procedure: receipt and verification result separate, effect dedupe/state transitions only after successful binding/business checks. Local signature checking may precede retention where safe, but no universal already-authenticated-ingress assumption. Duplicate messages versus legitimate later statuses differ; per-origin economic/idempotency ledger preserves exactly-once local effects without promising exactly-once provider delivery.

## IR05: typed action plans, independent authorities and per-effect slots
Initial ResourceBinding remains view/connect/start/review only. Add PROPOSED ApplyAuthority/1: authority_id, controller/delegate identity, provider/resource/environment, actions, role/delegation evidence, grant epoch, validity/revocation. It is distinct from Reader/start consent and does not widen it. Delegation states principal, delegate, exact resources/actions/expiry and who can revoke; no implied transitive delegation or host authority from source approval.

Build immutable ActionPlan/1 with exact effect DAG and conditional recovery branches: slot_id, provider/resource/environment, operation, intended artifact/config/state/trigger/budget digests, required authority IDs, required controllers, expected versions, cardinality=1 and dependencies. Derive required approvers from actual resource control/delegation (source/Git, registry/source-store, host, data/callback, financial if any), not a model-supplied list. Financial compensation is separate explicit financial authority/action plan; apply/rollback never implies refund permission.

Each controller issues ApplyApproval for the exact plan digest and only their authorised resources/actions. ApprovalSet/1 lists required approvals and authority epochs, all satisfying each effect slot; completeness must be verified before allowing its dependent effects. One controller can cover multiple roles only with explicit current evidence. Any missing/expired/revoked required approval blocks affected future slots; don't take union of partial permissions as authority nobody holds.

Plan endorsement is not consumed by the first write and is not reusable for arbitrary extra writes. Each EffectIntent reserves ONE immutable slot atomically with approval-set/current-authority/target-resource-fence checks. That slot transitions reserved→submitted→observed/failed/unknown; same effect retry/reconcile retains identity, cannot spend another slot or repeat an observed successful effect. A retry within provider idempotency semantics is the same effect; otherwise reconcile/hold. Duplicate merge/deploy requests do not gain extra cardinality. Cancel orders on the same plan/effect locks and fences all remaining slots.

Approval expiry after publication but before deployment denies new deploy; preserve known publication and request refreshed approval for exact remaining current plan. Previously dispatched effect may finish; read-reconcile under current read authority, no false undo. Revocation by one required controller invalidates their affected authority and dependent future slots, not erased history. Material source/tree/artifact/config/target/trigger/state changes create a new action-plan digest and new required approvals. Newly approved recovery uses current state and authority; old approval is not resurrected.

## IR07: staged exit and an independent bounded exit-check executor
A service cannot revoke all its operational capabilities then secretly use them to restart/recover. Choose a prequalified merchant-owned ExitCheck executor independent of GoldGraft control plane/worker/credentials. For the first qualification profile this may be an ALREADY APPROVED merchant-account workflow with fixed trusted code/image, short-lived host restart/read/current-compatible recovery capability and private state/handler observation endpoints. Such a workflow must exist/be separately provisioned with proper owner authority before final delivery; Publisher does not obtain Workflows write or install a privileged workflow by implication. No qualified executor means exit qualification held before a disruptive test; do not ask merchant to improvise scripts at the end.

Before disconnect, controller approves ExitCheckPlan/1: exact target/resource reservation, final artifact/config/state/provenance, observation criteria, permitted single restart, bound recovery branch, budget/deadline, evidence destination, safe failure outcome/owner and executor identity. Merchant-owned private evidence store and verification/signing roots remain available independently. Executor may inspect required private continuity locally and emits redacted signed results; no raw credentials/customer data transferred to public evidence or unapproved processor.

Sequence: (Q0) verify final merchant assets/current live outcome and ready executor; (Q1) fence/stop GoldGraft ordinary acquisition/model/mutation/worker capabilities, revoke ordinary remote grants after shared-use checks; (Q2) execute pre-authorised merchant restart/observations/recovery while GoldGraft cannot act; (Q3) reconcile signed results through an explicitly disclosed temporary read-only EXIT-EVIDENCE capability, not ordinary host/source access; (Q4) revoke/expire that remaining read capability and report its acknowledgement separately, then observe authorised public/merchant evidence. If full ordinary remote revocation acknowledgement missing, say pending, not denied everywhere.

Executor recovery is limited to approved current-compatible artifact/config/state route under reserved target; no financial compensation, blind oldDB restore or revival of revoked GoldGraft approval. If recovery scope inadequate, executor enters approved safe hold and alerts responsible merchant/controller through its preconfigured operating route; no Completed claim. GoldGraft case truthfully records known outcome/pending evidence, does not require merchant technical finishing as a hidden step. Actual independent executor readiness, permission mapping, restart/private observations, failure route and post-revocation continuity remain qualification gates.
