# Render delivery, effective configuration and durable state

Status: Plan3 engineering on paper, 6 November 2026. No implementation, account change, deployment, live payment/model/worker job or agent-internal design. CURRENT means inspected existing contract; all new lifecycle states/interfaces/modules below are PROPOSED. Vendor/account/runtime qualification gates remain open.

## First qualified deployment profile, not current infrastructure
Image-backed Render web service, linux/amd64 single-platform qualified image digest, controlled selected service/workspace/environment, one instance for initial disk-backed flat-file reference; dedicated merchant-controlled persistent state directory, merchant-owned callback ingress/queue and registry/configuration. No production support implied by fixture availability. If account/service does not meet this profile, hold or qualify another explicit profile; do not silently migrate hosting or add paid resources. Git-backed route requires separate build/source/runtime/trigger qualification.

Secret-free effective configuration and runtime identity must be provided by a qualified merchant-owned pipeline/runtime observation mechanism. Existing Render env-vars GET returns values, not a safe names-only effective-config record, and instance listing contains no image/config/health fields. Do not fabricate provider configVersion/current-byte/per-instance digest. Planned first profile uses signed build/deploy configuration manifest with nonsecret settings/required secret references, and trusted side-effect-free runtime identity/config observation tied to the exact reviewed wrapper/verification key; wrapper key excluded from untrusted shop/model. Observe single-instance identity and expected artifact/config under explicit trusted-controller/provider assumptions. This does not prove every mutable live byte; any manual mutation/unexplained config or missing trustworthy correlation holds correspondence. Multiple instances remain unsupported until per-instance version/health evidence is qualified.

## Exact provider APIs and outcome handling
Base https://api.render.com/v1. Initial reader consumes only approved metadata GETs. Later host controller grants separately qualified Deploys Run (includes cancel/rollback, not exact-digest-only provider scope); broker enforces action/service/digest/current approval/generation. Services writes/secret reads/infrastructure changes are separate and denied unless the reviewed plan explicitly requires/grants them. No public scope introspection was established; effective grant and endpoint coverage remain account-qualification gates.

Image apply: POST /services/{serviceId}/deploys with body imageUrl equal to configured registry/name plus immutable digest. No commitId/buildId/deploy_only mixing. Persist effect intent before request. 201 documented deploy response may provide id; only id required, other fields optional. 202 has no documented body schema: never invent a returned deploy ID. Lost/202 response -> bounded paginated GET deploy list reconciliation using actual observed fields/time/approved identity; if unique attribution impossible, remain INCIDENT_UNKNOWN without replay. Single local effect lock does not exclude external controller deploys.

Poll known GET /services/{serviceId}/deploys/{deployId}. Pending states created/queued/build_in_progress/pre_deploy_in_progress/update_in_progress remain pending; build_failed/pre_deploy_failed/update_failed/canceled/deactivated do not establish candidate live. Missing/unknown status or read failure holds. live + optional image.ref/image.sha must agree with validated single-platform digest semantics, current selected live identity and operation-relevant application/config/state observation. Provider live alone is not payment proof. Re-read after observation to catch competing deployment.

Recovery POST /services/{serviceId}/rollback body deployId selects prior successful deploy and returns a NEW rollback deployment to track. It does not undo disk/database/financial effects or disable Git auto-deploys. POST /services/{serviceId}/restart documents no deploy-object response; do not expect returned deploy ID. Reconcile actual runtime/state after any restart. Exact permission mapping, queued deploy behaviour, rate/backoff/quotas and missing fields require account tests. Broker may cancel only known authorised deploy, and must consider that cancellation can release another queued deployment.

## Persistence and controlled maintenance
The PHP fixture's orders.json/IPN log cannot live on an ephemeral root. Require durable merchant-owned storage with explicit mount-only persistence and consistency/locking; do not run concurrent writers against unprotected flat files. Persistent disk is unavailable in build/predeploy/one-off jobs and prevents default zero-downtime replace semantics. First disk-backed profile therefore chooses an explicitly controller-approved maintenance/drain cutover, not automatic rolling zero downtime.

Before apply: verify durable independent callback receipt/queue and current origin-event routing, state snapshot/restore test on disposable copy, schema compatibility, existing pending transaction handling and exact maintenance impact. If absent, a version-bound approved prerequisite install/config/deployment is itself reviewed and verified before cutover; never hidden initial connection mutation. Block new checkout creation through authorised shop control; retain existing-session capture/return/refund/notification handling via qualified durable merchant route. Persist bounded original IPN input as UNVERIFIED before receipt acknowledgement, then validate/retry postback and apply business effects only after verification; REST webhook has its own correct raw-body/listener validation; ingress may not lose already acknowledged event while shop restarts. If safe drain/ingress cannot be established, do not apply.

Choose backward-compatible/expand-contract state migration where possible. For required disk changes, snapshot/quiesce and migration occur through qualified runtime/startup path after old writer stopped, not a predeploy job assuming disk access. Track monotonic economic events through maintenance. Original data snapshot is recovery input, not permission to overwrite newer orders. If schema/callback compatibility cannot hold, use forward repair/hold; no blind disk restore. Keep maintenance until target required checks pass, then reopen admission under current approval and observations. Business-visible interruption must be disclosed; timing is unmeasured.

After deployment/restart: verify artifact/config/current service identity, state persistence and required origin callbacks; source/publication status not enough. Preserve immutable registry digest/pull rights and merchant runtime credentials after GoldGraft removal. Registry tag update alone does not trigger image-backed deploy; later restarts can repull and fail if image/auth disappeared.
